\begin{center}\textbf{\Large ABSTRACT}\end{center}
\justifying
Serverless applications often spend a substantial part of their first-request latency loading dependencies. This project presents the Predictive Cold-Start Optimizer (PCSO), an application-level approach that combines static dependency analysis with runtime transition prediction. The static phase separates startup-critical imports from request-specific imports. The runtime phase learns likely endpoint transitions and preloads the predicted dependency closure before the next request arrives. Against an eager no-optimizer baseline, the evaluated system reduces blended code-loading latency from 31.36 ms to 4.77 ms and total response latency from 35.29 ms to 15.48 ms. These correspond to reductions of 84.8\% and 56.1\%, respectively. The static-only V1/FaaSLight stage provides a useful minimum-improvement reference but can shift heavy import cost into handler execution.

\vspace{0.5em}
\textbf{Keywords:} serverless computing, cold start, dependency analysis, lazy loading, transition prediction, preloading.

\chapter{INTRODUCTION}
\section{Overview}
Function-as-a-Service platforms create execution environments on demand. A newly created environment must initialize application code before it can serve its first request. The initialization cost is particularly visible in services that include database clients, SDKs, model wrappers, or media-processing libraries. Loading every dependency eagerly is simple, but it makes optional functionality part of the critical path.

This project evaluates a progression from an eager no-optimizer baseline to the final Predictive Cold-Start Optimizer (PCSO). The comparison retains the static-only V1/FaaSLight stage as a minimum-improvement reference. The central objective is to reduce code-loading latency without moving the same cost into handler execution.

\section{Motivation}
Static dependency analysis can identify imports that are not needed for every request, but static information alone does not reveal when a deferred dependency will be needed. Runtime transition information provides that missing temporal signal. If endpoint $A$ is commonly followed by endpoint $B$, the dependencies of $B$ can be prepared while the system is processing $A$.

\section{Objectives}
\begin{enumerate}[label={(\arabic*)}]
\item Classify dependencies into startup-critical and deferrable imports.
\item Learn endpoint transitions using an online first-order model.
\item Preload the predicted endpoint and its dependency closure.
\item Compare the baseline, V1/FaaSLight, and PCSO across multiple workload profiles.
\end{enumerate}

\section{Scope and contributions}
The work focuses on application-level initialization rather than changes to a cloud provider's scheduler or container runtime. The unit of optimization is an endpoint module and the set of local dependencies it can reach. This keeps the method portable: the same policy can be applied wherever the application controls its import boundary and has access to a warm execution environment.

The main contribution is the connection between two kinds of information. Static analysis provides a dependency manifest, while runtime observation provides ordering information between endpoint invocations. V1 uses only the first source of information. PCSO combines both sources and therefore has an opportunity to move heavy initialization work out of the next request's critical path.

\chapter{LITERATURE REVIEW}
\section{Serverless cold starts}
A serverless cold start includes environment creation, application initialization, dependency loading, and handler execution. The relative contribution of these stages varies with application size and workload. For lightweight services, dependency loading can be a substantial fraction of total latency; for heavy services, a deferred model or processing library can dominate the handler path instead.

\section{FaaSLight and static deferral}
FaaSLight describes application-level cold-start optimization through dependency analysis and selective lazy loading~\cite{faaslight}. Its key insight is that a dependency imported only on a conditional path need not be loaded before every request. This work adopts that principle as V1 and extends it with runtime transition prediction and preloading.

\section{Research gap}
Static deferral answers \textit{what} can be delayed, but not \textit{when} the delayed code will be needed. The remaining challenge is to avoid paying a large deferred import cost inside the next request. PCSO addresses this gap by combining static dependency information with a learned next-endpoint prediction.

\section{Comparison of approaches}
The three points in the evaluation have deliberately different responsibilities. The baseline establishes the cost of eager loading. V1 isolates the benefit of static analysis and lazy imports. PCSO measures the additional benefit of using sequence information to warm the next endpoint. This separation is important because a large reduction in import time does not necessarily imply a large reduction in total response time when the import cost is merely moved into the handler.

\chapter{PROPOSED METHODOLOGY}
\section{Static dependency analysis}
The analyzer inspects the source structure of each function. Imports at module scope are classified as indispensable because they are needed to construct the handler environment. Imports inside functions or conditional branches are classified as optional candidates for deferral. The classification changes the loading schedule, not the behavior of the handler.

The analysis is intentionally lexical rather than speculative. It does not attempt to infer the result of arbitrary program paths. A top-level import is therefore treated as startup-critical, while an import nested in a function or branch is eligible for deferred loading. Local application dependencies are retained in the manifest; standard-library and external dependencies are ignored by the runtime preloader when they are not part of the application workload.

\section{Transition prediction}
PCSO maintains a first-order Markov transition table. For an observed transition from endpoint $A$ to endpoint $B$, it increments $N(A,B)$. The next-endpoint probability is estimated as
\begin{equation}
P(B\mid A)=\frac{N(A,B)}{\sum_x N(A,x)}.
\end{equation}
The highest-probability endpoint is selected when its confidence reaches the configured threshold. If the confidence is low, the system falls back to the static-loading behavior.

Before any endpoint has been invoked, the transition table is empty. The first invocation therefore has no prediction and follows the V1 loading path. After the first completed transition, the corresponding row contains one observation. As more transitions are observed, the row estimates become more stable. Ties are resolved deterministically by the predictor's ordering, and the confidence threshold prevents speculative warming when the observed evidence is weak.

For example, if the row for endpoint $A$ contains seven observations of $A\rightarrow B$ and three observations of $A\rightarrow C$, then $P(B\mid A)=0.70$ and $P(C\mid A)=0.30$. PCSO warms $B$ when the threshold is 0.35; it does not warm $C$ as the top prediction for that row.

\section{Preloading policy}
After each invocation, PCSO records the completed transition and predicts the next endpoint. It then warms the predicted endpoint and its local dependency closure. The background preload time is tracked separately from request latency. If the next request matches the prediction, the module is already resident; otherwise, the request follows the static-loading path without changing functional correctness.

The runtime sequence is therefore: (1) load the current endpoint, (2) execute its handler, (3) update the transition table, (4) select a predicted endpoint if the confidence threshold is met, and (5) import the predicted endpoint and its indispensable and optional local dependencies into the warm set. The measured response ends after step (2); step (5) is reported as background preparation. This distinction prevents the benchmark from presenting background work as if it were part of the current request's latency.

\chapter{RESULTS AND ANALYSIS}
\section{Evaluation protocol}
The evaluation uses four workload profiles. Tier 1 represents lightweight CRUD and utility functions. Tier 2 represents medium enterprise services with authentication, validation, and persistence logic. Tier 3 represents heavy OCR, fraud-analysis, and media-processing pipelines. The blended profile samples 50\% Tier 1, 35\% Tier 2, and 15\% Tier 3 activity.

Each tiered profile contains 24 invocations and the blended profile contains 32. Fixed random seeds make the sequences repeatable. Each version is evaluated in an isolated runtime state. The reported metrics are mean import latency, mean handler latency, mean total response latency, p95 latency, resident memory, and predictive cache-hit rate.

For an invocation $i$, total response latency is computed as
\begin{equation}
T_i=T_{\mathrm{load},i}+T_{\mathrm{handler},i}.
\end{equation}
The percentage reduction of an optimized version $M$ relative to the baseline is
\begin{equation}
R_M=100\times\frac{\overline{T}_{\mathrm{baseline}}-\overline{T}_M}
{\overline{T}_{\mathrm{baseline}}}.
\end{equation}
The p95 is the latency value at the 95th percentile of the ordered invocation samples. Cache-hit rate is the fraction of invocations whose endpoint module was already present in the predicted warm set.

\section{Tier 3 analysis}
V1 reduces Tier 3 code-loading latency from 81.15 ms to 17.05 ms, but the heavy OCR, machine-learning, and media dependencies are then imported inside the handler. Consequently, total latency changes only from 89.47 ms to 88.98 ms. PCSO uses the observed transition history to warm the predicted heavy dependency closure before the request. Total Tier 3 latency therefore falls to 43.52 ms, a 51.4\% reduction relative to the baseline and a 51.1\% reduction relative to V1.

\section{Blended fleet analysis}
For the blended fleet, V1 reduces code-loading latency by 53.9\% and total latency by 28.7\%. PCSO improves those reductions to 84.8\% and 56.1\%. The tiered sequences produce higher prediction hit rates than the deliberately mixed fleet: 79.2\% for Tier 1, 66.7\% for Tier 2, 41.7\% for Tier 3, and 12.5\% for the blended profile.

\chapter{CONCLUSIONS AND FUTURE WORK}
\section{Conclusion}
PCSO combines static dependency analysis, transition prediction, and dependency-closure preloading. Against the true eager baseline, it reduces blended code-loading latency by 84.8\% and total response latency by 56.1\%. The three-way comparison clarifies the source of the gain: V1 removes optional imports from startup, while PCSO prevents heavy deferred imports from reappearing on the handler's critical path.

\section{Limitations and future work}
The evaluation is a controlled application-level benchmark rather than a measurement of a particular cloud provider's network, billing, or container scheduler. The dependency weights model relative initialization cost and should not be interpreted as provider-specific timings. The predictor is first-order and online; it can be inaccurate after an abrupt workload change. Future work should evaluate production traces, add confidence decay, enforce a memory budget, and move preloading to an asynchronous worker with explicit resource limits.
